# --- Tower: reference implementations held against the durable stores -------
# Each parity suite runs one scenario against BOTH the memory store and the Postgres one
# and requires the same answer, and the two are written deliberately differently - a held
# mutex against a locked row and a CAS, a Go comparison against a conditional upsert, a
# scan against a partial unique index - so agreement is a result rather than a tautology.
# The broker never builds a memory store (loadTowerSubsystem returns nil without a
# database), so they are unreachable by construction. Deleting them would delete the only
# thing that can tell you the durable store is wrong; that has already caught mem/PG
# divergence on re-attachment, live-key uniqueness, duplicate ids and a cap's expiry.

# --- Tower: the CONSUMER's half of the edge path ----------------------------
# SignAck produces the acknowledgement a consumer sends Roger Core about what it actually
# received. It is unreachable because no binary in this repo is yet an edge CONSUMER: the
# broker verifies acknowledgements (ParseAck) and settles on them (Reconcile), and the
# Station and Tower must never produce one - a Tower signing the consumer's account of the
# bytes would destroy the entire opposing-interest property that makes the evidence worth
# anything.
#
# So this is a genuine gap rather than a wiring miss, and it is the next build step: the
# rogerai client does not yet speak the edge path. Exercised end to end by
# cmd/roger-station/edge_test.go, which signs an acknowledgement over bytes that really
# crossed a real relay and reconciles it against the Station's real receipt.
internal/towercore/dispatch.SignAck

# from separate maps in separate processes. The in-process one is correct for a single broker
# and is what the tests exercise.
internal/towercore/dispatch.New

# --- the certificate is not yet used to AUTHENTICATE anything ---------------
# Nothing in production performs mutual TLS. A Tower authenticates by signing its HTTP
# requests (towerCaller), which is real authentication and is not what the approved spec
# describes: features/tower/job_and_settlement.feature has the outer channel mutually
# authenticated by TLS 1.3 bound to the Tower's identity and session.
#
# So these four - and isRevoked with them - are the verifying half of a layer that has not
# been built. CERTIFICATE revocation is therefore not enforced today. Tower revocation IS:
# it is enforced in the admission registry, which is what gates dispatch, so a revoked Tower
# gets no work. The gap is the channel layer, not the removal.
#
# Kept because they are the correct implementations to wire when mTLS lands, and deleting
# them would mean rewriting the revocation check from scratch at that point.
method internal/towercore/cert.AuthenticateAs
method internal/towercore/cert.ProveMatches
method internal/towercore/cert.RevokedSerials
